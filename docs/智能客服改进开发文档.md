# RAG 智能客服系统改进开发文档

## 1. 文档定位

本文档用于指导当前 RAG 智能客服问答系统的后续改造。项目目标定位为：

**准生产级简历项目**

也就是说，本项目不追求企业级完整上线能力，但需要明显区别于普通课程 Demo，重点体现：

- 完整的智能客服业务闭环。
- 登录鉴权和角色权限控制。
- 用户会话持久化和数据隔离。
- RAG 检索、FAQ、订单物流、转人工工单的协同。
- 数据看板、用户反馈、未解决问题沉淀和 FAQ 优化闭环。
- 可扩展的工程架构，便于面试时讲清楚设计取舍。

本文档只描述开发方案和阶段计划，不代表已经开始修改业务代码。

## 2. 当前系统概况

当前系统已经具备较好的基础能力：

- 前端：React + Ant Design，包含聊天窗口、会话列表、知识库管理、FAQ 管理、数据看板、模型配置、登录注册等页面。
- 后端：FastAPI，提供聊天、WebSocket 流式输出、知识库上传、FAQ 管理、看板统计、认证、会话、模型配置等接口。
- RAG：Milvus 向量检索、BGE-M3 embedding、BM25 稀疏检索、RRF 融合、reranker、LLM 生成。
- 客服能力雏形：意图识别、FAQ 缓存、订单查询、物流查询、联网搜索、内容过滤。

当前系统更像“RAG 知识问答 + 客服页面”，距离准生产级智能客服还差以下闭环：

- 聊天必须登录，但当前聊天链路与登录用户、会话、消息表还没有完整绑定。
- 普通用户、客服运营、管理员的权限边界还不够明确。
- 模型配置应由管理员统一管理，普通用户不应自行传入或使用别人的模型配置。
- 普通用户不应看到完整知识库来源和 chunk 内容，只应看到简化来源标识。
- 订单/物流仍是 mock 函数，需要抽象成可替换的业务服务层。
- 转人工目前只是 prompt 层建议，需要做成真实工单闭环。
- FAQ 需要从字符串模糊匹配升级为语义检索。
- 低置信度、没帮助、转人工问题需要沉淀到未解决问题池。

## 3. 已确认的核心决策

### 3.1 项目标准

选择 **B：准生产项目**。

开发时按真实客服系统的基本结构设计，但控制复杂度，避免引入过重的企业级系统。

### 3.2 聊天访问

聊天必须登录。

未登录用户访问聊天页应跳转登录页。WebSocket 连接也需要鉴权，后端校验 token 后才能建立或处理聊天请求。

### 3.3 模型配置

采用管理员统一配置模型。

普通用户不配置自己的 API Key，也不应在聊天请求中指定任意 `model_config_id`。后端聊天链路统一使用管理员设置的默认模型配置，或 `.env` 中的默认配置。

### 3.4 来源展示

普通用户不展示完整知识库来源。

- 普通用户只看到简化来源，例如“来自知识库”“来自 FAQ”“来自订单系统”“来自物流系统”“来自联网搜索”。
- staff/admin 可以查看完整来源，包括文件名、片段内容、chunk、检索分数等。

### 3.5 会话保存

用户消息和 AI 回复由后端聊天接口统一保存。

前端不负责在聊天完成后单独调用消息接口保存，避免流式中断、刷新页面或网络异常导致数据不一致。

### 3.6 转人工

转人工采用工单模式。

当系统无法解决问题、用户要求人工、低置信度连续出现或涉及高风险业务时，自动生成工单，并向用户展示工单编号和状态。

### 3.7 订单物流

订单/物流抽象为业务服务层，当前仍使用 mock 实现。

这样既能保持开发成本可控，又能在简历和面试中体现可对接真实 OMS/WMS/ERP 系统的架构设计。

### 3.8 FAQ 检索

FAQ 单独做 embedding 语义检索，支持相似问。

FAQ 作为客服高频问题的高优先级知识源，优先于普通知识库 RAG。

### 3.9 低置信度策略

低置信度时不直接转人工。

第一次低置信度先引导用户补充问题；同一会话连续低置信度或涉及高风险问题时，再触发转人工/工单。

### 3.10 用户反馈

用户反馈采用细分原因。

每条 AI 回复支持“有帮助/没帮助”，选择“没帮助”时可选择原因，例如答非所问、信息不完整、信息过期、没解决问题、需要人工客服等。

## 4. 阶段一：稳定性和安全基线

### 4.1 阶段目标

先修复明显工程问题，并建立准生产项目必须具备的基础安全和权限边界。

### 4.2 开发任务

#### 4.2.1 修复前端构建错误

当前 `npx.cmd tsc --noEmit` 会失败：

- `frontend/src/services/conversationService.ts` 引入了 `Message`，但 `frontend/src/types/chat.ts` 没有导出该类型。
- `frontend/src/services/userService.ts` 和 `frontend/src/stores/useAuthStore.ts` 引用了 `@/types/auth`，但该文件不存在。

建议补齐类型定义，保证 `npm run build` 可以通过。

#### 4.2.2 修复后端明显 bug

已发现问题：

- `backend/api/conversations.py` 中路由函数 `delete_conversation` 与 DAO 函数同名，存在命名遮蔽风险。
- 模型配置路由中 `/{config_id}` 可能影响 `/default` 这类固定路径匹配，建议固定路径放在动态路径前。

#### 4.2.3 角色权限设计

保留三类角色：

- `user`：普通用户，聊天、查看自己的会话和工单、提交反馈。
- `staff`：客服/运营，处理工单、维护 FAQ、查看部分看板、查看完整来源。
- `admin`：管理员，拥有全部权限，包括知识库、用户、模型配置、系统设置。

#### 4.2.4 接口权限范围

建议权限如下：

| 模块 | user | staff | admin |
| --- | --- | --- | --- |
| 聊天 | 是 | 是 | 是 |
| 自己的会话 | 是 | 是 | 是 |
| 自己的工单 | 是 | 是 | 是 |
| 全部工单 | 否 | 是 | 是 |
| FAQ 管理 | 否 | 是 | 是 |
| 知识库管理 | 否 | 否 | 是 |
| 数据看板 | 否 | 是 | 是 |
| 模型配置 | 否 | 否 | 是 |
| 用户管理 | 否 | 否 | 是 |
| 系统设置 | 否 | 否 | 是 |

#### 4.2.5 WebSocket 鉴权

WebSocket 聊天也必须鉴权。

可选实现：

- 连接参数携带 token：`ws://host/api/ws/chat?token=xxx`
- 或连接建立后第一条消息发送 token。

建议后端统一解析 token，校验成功后将 `current_user` 绑定到本次连接上下文。

#### 4.2.6 模型配置安全

普通用户聊天请求不再接收或不再信任 `model_config_id`。

后端选择模型配置的优先级建议：

1. 管理员配置的默认模型。
2. `.env` 中的默认模型。

模型配置相关接口只允许 admin 访问。

#### 4.2.7 来源脱敏

后端返回消息时区分：

```json
{
  "public_sources": [
    { "type": "knowledge_base", "label": "来自知识库" }
  ],
  "debug_sources": [
    {
      "text": "...",
      "source": "售后政策.pdf",
      "score": 87,
      "chunk_index": 12
    }
  ]
}
```

普通用户只能看到 `public_sources`。staff/admin 可查看 `debug_sources`。

#### 4.2.8 上传安全

知识库上传需要做基础加固：

- 后端限制文件大小。
- 文件扩展名白名单。
- 文件名净化，防止路径穿越。
- MIME 类型与扩展名双重校验。
- `/kb/upload-dir` 只能索引白名单目录，或仅 admin 可用。
- Milvus 查询表达式中涉及用户输入时需要转义。

#### 4.2.9 生产配置基线

- `DEBUG` 从 `.env` 配置，生产默认 `False`。
- `JWT_SECRET_KEY` 必须从环境变量读取，不使用默认弱密钥。
- CORS 改为可配置白名单。
- debug 接口移除或仅 admin 可访问。

### 4.3 阶段一完成标准

- 前端 `npm run build` 通过。
- 后端已修复明显接口 bug。
- 聊天和 WebSocket 均要求登录。
- 普通用户无法访问管理接口。
- 模型配置只允许 admin 管理。
- 普通用户看不到完整来源。
- 上传接口具备基础安全校验。

## 5. 阶段二：会话持久化闭环

### 5.1 阶段目标

让聊天不再依赖前端本地状态，而是形成登录用户、会话、消息、来源、意图、耗时的完整后端闭环。

### 5.2 推荐流程

1. 用户登录后进入聊天页。
2. 前端如果没有当前会话，调用后端创建会话。
3. 用户发送问题时携带 `conversation_id`。
4. 后端保存用户消息。
5. 后端执行意图识别、FAQ、RAG、订单物流或联网搜索。
6. 后端流式返回 AI 回复。
7. 后端在流式完成后保存 AI 回复。
8. 前端刷新页面后可恢复历史会话和消息。

### 5.3 WebSocket 入参

```json
{
  "conversation_id": 123,
  "query": "我的订单什么时候到？",
  "kb_only": false,
  "web_search": false
}
```

说明：

- 不再让普通用户传 `model_config_id`。
- `conversation_id` 必须属于当前登录用户。

### 5.4 WebSocket 出参

流式 token：

```json
{
  "type": "token",
  "data": "您好，"
}
```

来源：

```json
{
  "type": "sources",
  "data": {
    "public_sources": [
      { "type": "faq", "label": "来自 FAQ" }
    ]
  }
}
```

完成：

```json
{
  "type": "done",
  "data": {
    "message_id": 456,
    "intent": "faq",
    "latency_ms": 1280,
    "confidence": 0.86,
    "hit_faq": true,
    "need_handoff": false
  }
}
```

### 5.5 消息表建议增强字段

当前消息表已有 `role/content/sources/intent/latency_ms`，建议增强为：

```text
messages
- id
- conversation_id
- role: user / assistant
- content
- public_sources
- debug_sources
- intent
- latency_ms
- confidence
- need_handoff
- status: completed / streaming / interrupted / error
- created_at
```

### 5.6 流式中断处理

流式输出时建议：

- 收到用户问题后立即保存用户消息。
- AI 回复在内存中累积。
- 正常完成时保存完整 AI 回复。
- 用户主动停止时保存 `status=interrupted`。
- 模型异常时保存 `status=error` 和错误提示。

### 5.7 会话标题

简历项目建议先用简单规则：

- 第一条用户消息前 20-30 个字作为标题。
- 后续可选增强：LLM 自动总结标题。

### 5.8 阶段二完成标准

- 前端创建会话调用后端接口。
- 聊天请求必须带后端 `conversation_id`。
- 用户消息和 AI 回复由后端统一保存。
- 刷新页面后能恢复历史会话和消息。
- 普通用户只能访问自己的会话和消息。
- AI 消息记录意图、耗时、置信度、来源和状态。

## 6. 阶段三：客服业务闭环

### 6.1 阶段目标

把系统从“问答机器人”升级为“客服系统”，支持转人工、工单、订单物流追问和业务服务抽象。

### 6.2 转人工工单

#### 6.2.1 触发条件

先使用规则 + 置信度即可：

- 用户明确说“转人工”“人工客服”“投诉”“客服介入”。
- RAG 检索无结果或置信度低。
- 同一会话连续 2 次低置信度。
- 用户连续 2 次反馈“没帮助”。
- 涉及退款金额、修改地址、取消订单、投诉、账号安全。
- 订单/物流缺少关键信息且多次追问失败。
- LLM 或业务接口异常。

#### 6.2.2 工单状态

```text
open        已创建
processing 处理中
resolved    已解决
closed      已关闭
```

#### 6.2.3 工单表建议

```text
support_tickets
- id
- ticket_no
- user_id
- conversation_id
- message_id
- category
- priority
- status
- summary
- user_question
- ai_answer
- public_sources
- debug_sources
- assigned_to
- staff_note
- created_at
- updated_at
```

#### 6.2.4 权限

- 普通用户：只能查看自己的工单状态。
- staff：可以查看、处理、备注、修改状态。
- admin：可以查看全部工单，并管理分配。

#### 6.2.5 前端表现

聊天中显示：

```text
当前问题已为您生成工单：TK202605130001
客服人员会尽快处理，您可以在“我的工单”中查看进度。
```

新增页面：

- 用户侧：我的工单。
- staff/admin：工单管理。

### 6.3 订单/物流服务抽象

#### 6.3.1 目录建议

```text
backend/business/
- __init__.py
- order_service.py
- logistics_service.py
- ticket_service.py
```

#### 6.3.2 服务接口建议

```python
class OrderService:
    async def get_order(self, user_id: int, order_id: str | None):
        ...

    async def list_recent_orders(self, user_id: int, limit: int = 5):
        ...


class LogisticsService:
    async def get_trace(
        self,
        user_id: int,
        order_id: str | None,
        tracking_no: str | None,
    ):
        ...
```

当前先实现 mock 服务，后续可替换为真实 OMS/WMS/ERP API。

### 6.4 Slot Filling

订单/物流问题需要先提取关键信息：

- 订单号。
- 运单号。
- 手机号后四位。
- 商品名。
- 时间范围。

如果用户说“我的快递到哪了”，但没有订单号：

- 如果用户有最近订单，展示最近订单供选择。
- 如果没有最近订单，提示输入订单号或手机号后四位。
- 不直接返回随机 mock 数据。

### 6.5 结构化卡片

订单和物流回复建议使用结构化卡片展示：

- 订单号。
- 商品。
- 状态。
- 金额。
- 下单时间。
- 物流节点。
- 预计送达时间。

### 6.6 阶段三完成标准

- 支持自动生成工单。
- 用户可查看自己的工单。
- staff/admin 可处理工单。
- 订单/物流逻辑已抽象为服务层。
- 缺少订单号或运单号时会追问，而不是随机返回 mock。
- 订单/物流回复具备结构化展示。

## 7. 阶段四：RAG 质量优化

### 7.1 阶段目标

提高回答准确率，减少幻觉，让系统回答更像受控的客服，而不是通用聊天机器人。

### 7.2 FAQ 语义检索

FAQ 不再只靠字符串模糊匹配，建议新增：

- FAQ embedding。
- 相似问列表。
- FAQ 分类。
- FAQ 状态。
- FAQ 优先级。
- 命中分数。

FAQ 字段建议：

```text
faq_pairs
- id
- question
- answer
- similar_questions_json
- category
- tags
- status: draft / active / inactive
- priority
- effective_from
- effective_to
- frequency
- created_by
- updated_by
- created_at
- updated_at
```

### 7.3 推荐问答流程

```text
用户问题
-> 内容安全检查
-> 意图识别
-> FAQ 精确匹配
-> FAQ 语义检索
-> 知识库 RAG
-> 低置信度追问
-> 连续失败后转人工/工单
```

### 7.4 相似问示例

```json
{
  "question": "退换货政策是什么？",
  "similar_questions": [
    "商品不满意能退吗？",
    "七天无理由怎么退？",
    "换货流程是什么？"
  ]
}
```

### 7.5 中文 BM25 优化

当前中文 BM25 使用空格切词效果较弱。

建议：

- 简单版本：接入 `jieba`。
- 高级版本：使用 BGE-M3 sparse 能力。

对准生产简历项目而言，先使用 `jieba` 即可，便于实现和解释。

### 7.6 BM25 启动重建

服务启动时从 Milvus 或知识库索引数据重建 BM25 内存语料，避免重启后稀疏检索为空。

### 7.7 置信度策略

统一返回以下字段：

- `retrieval_score`
- `rerank_score`
- `faq_score`
- `confidence`
- `need_handoff`

置信度可先用规则融合，不需要一开始就做复杂模型：

```text
confidence = max(faq_score, rerank_score, dense_score)
```

后续可加入意图置信度、来源数量、用户反馈等因素。

### 7.8 低置信度处理

第一次低置信度：

```text
当前知识库中没有找到足够明确的信息。您可以补充商品型号、订单号或具体问题，我会继续帮您查询。
```

同一会话连续 2 次低置信度：

- 自动生成工单，或
- 显示“转人工”按钮。

高风险问题低置信度时可直接转人工：

- 退款金额。
- 投诉。
- 改地址。
- 取消订单。
- 账号安全。

### 7.9 强来源约束

以下问题必须基于来源回答：

- 价格。
- 库存。
- 优惠活动。
- 售后政策。
- 保修条款。
- 退款金额。
- 发票规则。

如果来源中没有明确答案，应拒答或转人工，不让 LLM 自由编造。

### 7.10 轻量评测集

建议增加：

```text
backend/evals/customer_service_cases.json
```

包含：

- 标准 FAQ 问法。
- FAQ 相似问。
- 知识库问答。
- 无答案问题。
- 订单物流问题。
- 转人工问题。
- prompt 注入问题。

### 7.11 阶段四完成标准

- FAQ 支持语义检索和相似问。
- 中文 BM25 分词优化。
- 服务启动可重建 BM25 语料。
- 回答结果包含置信度。
- 低置信度先追问，连续失败再转人工。
- 高风险问题执行强来源约束。

## 8. 阶段五：运营与评估

### 8.1 阶段目标

形成客服运营闭环，让系统可以根据用户反馈和未解决问题持续优化。

### 8.2 用户反馈

每条 AI 回复支持：

- 有帮助。
- 没帮助。

如果选择“没帮助”，弹出原因：

- 答非所问。
- 信息不完整。
- 信息可能过期。
- 没解决问题。
- 需要人工客服。
- 其他。

### 8.3 反馈表建议

```text
message_feedbacks
- id
- user_id
- conversation_id
- message_id
- rating: helpful / unhelpful
- reason
- comment
- created_at
```

### 8.4 未解决问题池

以下情况自动进入未解决问题池：

- 用户点“没帮助”。
- 连续低置信度。
- 触发转人工。
- 工单创建。
- 检索无来源。
- LLM 异常。

字段建议：

```text
unresolved_questions
- id
- user_id
- conversation_id
- message_id
- question
- ai_answer
- reason
- intent
- confidence
- sources
- status: pending / converted_to_faq / ignored / resolved
- created_at
- updated_at
```

### 8.5 FAQ 草稿闭环

staff/admin 可以从未解决问题创建 FAQ 草稿：

1. 自动带入用户问题。
2. AI 答案可作为草稿参考。
3. 默认不直接发布。
4. 运营编辑后发布。
5. 发布后 FAQ 进入语义检索。

### 8.6 看板指标

建议增加：

- 总咨询量。
- FAQ 命中率。
- RAG 命中率。
- 有帮助率。
- 没帮助率。
- 未解决问题数量。
- 转人工率。
- 工单解决率。
- FAQ 转化数量。
- 高频未解决问题。
- 平均响应耗时。
- 意图分布。

### 8.7 阶段五完成标准

- AI 回复支持细分反馈。
- 反馈数据落库。
- 低置信度、没帮助、转人工问题进入未解决问题池。

## 11. 已确认补充决策

以下内容为围绕后续待确认问题讨论后的定稿决策。

### 11.1 staff 会话查看范围

staff 不能查看所有用户会话。

权限规则：

- `user`：只能查看自己的会话。
- `staff`：只能查看进入客服处理流程的会话。
- `admin`：可以查看全部会话，用于审计和管理。

进入客服处理流程的会话包括：

- 已转人工会话。
- 已生成工单的会话。
- 用户反馈“没帮助”的会话。
- 低置信度并进入未解决问题池的会话。

这样可以在客服处理权限和用户隐私之间取得平衡，也更符合准生产项目的数据隔离设计。

### 11.2 admin 多模型配置

admin 支持多个模型配置，并设置一个默认模型。

规则：

- 只有 `admin` 可以访问模型配置页面和接口。
- 支持新增、编辑、删除多个模型配置。
- 每次只能有一个 `is_default = true`。
- 聊天链路统一使用默认模型。
- 如果没有默认模型，则 fallback 到 `.env` 配置。
- API Key 加密存储，只展示掩码。
- 普通用户前端不显示模型选择器，后端也不接受普通用户指定模型。

该设计可以体现管理员统一管理模型能力，同时避免普通用户自带 API Key 带来的安全和产品复杂度。

### 11.3 工单分配机制

工单采用“公共池 + staff 领取”的简化分配机制。

规则：

- 新工单默认进入公共工单池，`assigned_to = null`。
- 任意 `staff` 可以领取未分配工单。
- 领取后 `assigned_to = 当前 staff_id`。
- 领取后工单状态变为 `processing`。
- 已领取工单只有领取人和 `admin` 可以处理。
- 其他 `staff` 可以查看，但不能修改状态和备注。
- `admin` 可以重新分配工单。

工单状态保持简单：

```text
open        已创建
processing 处理中
resolved    已解决
closed      已关闭
```

该设计比纯公共池更像真实客服系统，但复杂度仍然可控。

### 11.4 订单/物流 mock 数据隔离

订单/物流 mock 数据需要按用户隔离。

规则：

- 订单查询必须基于当前登录用户 `user_id`。
- 普通用户只能查看自己的 mock 订单和物流。
- staff/admin 在处理工单时，可以查看该工单关联用户的订单/物流上下文。
- mock 实现阶段可以简单使用 `user_id` 映射不同订单。
- 服务接口必须保留 `user_id` 参数，方便后续替换真实业务系统。

这样可以避免所有用户看到同一批 mock 订单，也能体现用户数据隔离设计。

### 11.5 FAQ 草稿审核流程

FAQ 草稿采用简化审核流程。

规则：

- `staff` 可以从未解决问题创建 FAQ 草稿。
- `staff` 可以编辑草稿。
- `staff` 不能发布 FAQ。
- `admin` 可以发布或驳回 FAQ 草稿。
- `admin` 可以直接创建并发布 FAQ。
- 只有 `active` 状态 FAQ 进入语义检索。
- 草稿、驳回、停用状态不参与用户问答。

FAQ 状态建议：

```text
draft      草稿
rejected   已驳回
active     已发布
inactive   已停用
```

该设计能体现知识质量控制，同时不会引入过重的审核流。

### 11.6 未解决问题池去重策略

未解决问题池采用简单文本去重 + 频次统计。

规则：

- 对用户问题做规范化：
  - 去首尾空格。
  - 转小写。
  - 去常见标点。
  - 合并连续空白。
- 生成 `normalized_question`。
- 如果已有相同 `normalized_question` 的未解决问题：
  - `frequency += 1`。
  - 更新 `last_seen_at`。
  - 记录最近一次样例问题或会话引用。
- 如果没有匹配记录，则创建新记录。
- 看板展示高频未解决问题排行。
- FAQ 草稿可以从高频未解决问题生成。

建议字段增加：

```text
unresolved_questions
- normalized_question
- frequency
- last_seen_at
```

语义聚类暂不作为第一版功能，可作为后续增强项。

### 11.7 看板时间范围

看板支持时间范围筛选，第一版只做预设范围。

支持范围：

- `today`
- `7d`
- `30d`

默认建议使用 `7d`，更适合查看近期客服运营问题。

接口建议：

```http
GET /api/dashboard?range=7d
```

暂不做自定义日期范围，自定义开始/结束日期可作为后续增强。
