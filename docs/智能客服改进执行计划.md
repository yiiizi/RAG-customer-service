# RAG 智能客服系统改进执行计划

## 1. 计划说明

本文档基于 `docs/智能客服改进开发文档.md` 编写，用于后续直接进入代码修改阶段。

本文档只包含执行计划，不包含项目介绍或包装内容。

执行原则：

- 先修稳定性和权限基线。
- 再打通登录态会话持久化。
- 再补客服业务闭环。
- 最后做 RAG 质量优化和运营闭环。
- 每个阶段尽量独立验收，避免一次性大改。
- 后端数据模型、权限和接口先行，前端页面随后适配。

## 2. 总体阶段

```text
阶段一：稳定性、安全和权限基线
阶段二：登录态会话持久化闭环
阶段三：客服业务闭环
阶段四：RAG 质量优化
阶段五：运营闭环
```

阶段一和阶段二是后续所有功能的基础，不建议跳过。

## 3. 阶段一：稳定性、安全和权限基线

### 3.1 目标

- 前端可以正常构建。
- 后端明显 bug 修复。
- 聊天必须登录。
- WebSocket 必须鉴权。
- 管理接口按角色鉴权。
- 模型配置由 admin 统一管理。
- 普通用户不展示完整来源。
- 上传接口具备基础安全校验。

### 3.2 后端任务

#### 3.2.1 修复会话删除命名遮蔽

涉及文件：

- `backend/api/conversations.py`
- `backend/mysql_module/conversations.py`

修改要点：

- 避免路由函数 `delete_conversation` 与 DAO 函数同名。
- 可将 DAO 导入改为 `delete_conversation_record`。
- 或将路由函数改名为 `delete_conversation_route`。

验收标准：

- `DELETE /api/conversations/{conversation_id}` 可以删除当前用户自己的会话。
- 删除不存在或不属于自己的会话返回 404。

#### 3.2.2 调整模型配置路由顺序

涉及文件：

- `backend/api/model_config.py`

修改要点：

- 固定路径 `/default` 放到动态路径 `/{config_id}` 之前。
- 避免 `/default` 被当成 `config_id` 解析。

验收标准：

- `GET /api/model-configs/default` 正常返回默认模型或 404。
- `GET /api/model-configs/{config_id}` 正常查询指定配置。

#### 3.2.3 增加角色权限依赖

涉及文件：

- `backend/middleware/auth.py`
- `backend/api/routes.py`
- `backend/api/admin.py`
- `backend/api/model_config.py`
- `backend/api/conversations.py`

修改要点：

- 保留 `get_current_user`。
- 增加 `get_current_staff_user`。
- 完善 `get_current_admin_user`。
- 可选增加通用依赖：`require_roles(["staff", "admin"])`。

角色权限：

- `user`：聊天、自己的会话、自己的工单、提交反馈。
- `staff`：工单、FAQ、部分看板、完整来源查看。
- `admin`：知识库、模型配置、用户管理、系统设置、全部看板。

验收标准：

- 未登录访问受保护接口返回 401。
- 普通用户访问管理接口返回 403。
- staff 可访问 FAQ、工单、看板。
- admin 可访问模型配置、知识库、用户管理。

#### 3.2.4 聊天接口强制登录

涉及文件：

- `backend/api/routes.py`
- `backend/api/schemas.py`
- `backend/rag_qa/pipeline.py`

修改要点：

- `POST /api/chat` 增加 `current_user = Depends(get_current_user)`。
- 普通用户请求中传入的 `model_config_id` 不再信任。
- 聊天链路统一使用 admin 默认模型或 `.env` 配置。

验收标准：

- 未登录不能调用非流式聊天。
- 普通用户传 `model_config_id` 不影响模型选择。

#### 3.2.5 WebSocket 鉴权

涉及文件：

- `backend/api/routes.py`
- `backend/utils/security.py`
- `backend/middleware/auth.py`
- `frontend/src/hooks/useWebSocket.ts`
- `frontend/src/services/chatService.ts`

推荐实现：

- WebSocket URL 携带 token：`ws://host:8000/api/ws/chat?token=xxx`。
- 后端从 query 参数取 token 并校验 JWT。
- token 无效或缺失时关闭连接。

验收标准：

- 无 token 连接被关闭。
- token 无效连接被关闭。
- token 有效后才能发送聊天消息。

#### 3.2.6 管理接口补权限

涉及文件：

- `backend/api/routes.py`
- `backend/api/model_config.py`
- `backend/api/admin.py`

接口权限：

- `/api/kb/*`：admin。
- `/api/faq/*`：staff/admin。
- `/api/dashboard`：staff/admin。
- `/api/settings`：admin。
- `/api/model-configs/*`：admin。

验收标准：

- 普通用户不能上传知识库、维护 FAQ、访问模型配置。
- staff 可以维护 FAQ 和查看看板。
- admin 可以访问全部管理接口。

#### 3.2.7 模型配置改为 admin 统一配置

涉及文件：

- `backend/api/model_config.py`
- `backend/mysql_module/model_config.py`
- `backend/rag_qa/pipeline.py`
- `frontend/src/pages/ModelConfig/index.tsx`
- `frontend/src/pages/Chat/ChatInput.tsx`
- `frontend/src/stores/useChatStore.ts`

修改要点：

- 模型配置接口只允许 admin。
- 支持多个模型配置。
- 每次只能有一个默认模型。
- 后端聊天时读取默认模型。
- 没有默认模型时使用 `.env`。
- 普通用户聊天输入框移除模型选择器。

验收标准：

- admin 可维护多个模型配置。
- 只有一个默认模型。
- 普通用户聊天统一使用默认模型。
- 普通用户看不到模型选择器。

#### 3.2.8 来源脱敏结构

涉及文件：

- `backend/api/schemas.py`
- `backend/rag_qa/pipeline.py`
- `backend/rag_qa/retriever.py`
- `frontend/src/pages/Chat/SourcePanel.tsx`
- `frontend/src/pages/Chat/ChatWindow.tsx`
- `frontend/src/types/chat.ts`

修改要点：

- 后端区分 `public_sources` 和 `debug_sources`。
- 普通用户只获取或只展示 `public_sources`。
- staff/admin 可以查看 `debug_sources`。

建议结构：

```json
{
  "public_sources": [
    { "type": "knowledge_base", "label": "来自知识库" }
  ],
  "debug_sources": [
    {
      "text": "...",
      "source": "售后政策.pdf",
      "score": 87,
      "chunk_index": 12
    }
  ]
}
```

验收标准：

- 普通用户聊天页不显示文件名、chunk、完整片段。
- staff/admin 可查看完整来源。

#### 3.2.9 上传安全加固

涉及文件：

- `backend/api/routes.py`
- `backend/config/settings.py`
- `backend/offline_kb/indexer.py`
- `backend/rag_qa/milvus_store.py`

修改要点：

- 后端限制文件大小。
- 文件名净化，禁止路径穿越。
- 文件扩展名白名单。
- 可选：MIME 类型校验。
- `/kb/upload-dir` 限制为 admin，并限制白名单目录，或第一版禁用。
- Milvus 表达式拼接涉及用户输入时做转义。

验收标准：

- 超大文件上传被拒绝。
- 非白名单扩展名被拒绝。
- 路径穿越文件名被拒绝或安全重命名。
- 普通用户不能调用知识库上传和删除。

### 3.3 前端任务

#### 3.3.1 修复 TypeScript 构建错误

涉及文件：

- `frontend/src/types/chat.ts`
- `frontend/src/types/auth.ts`
- `frontend/src/services/conversationService.ts`
- `frontend/src/services/userService.ts`

修改要点：

- 增加 `Message` 类型，或统一使用 `ChatMessage`。
- 新增 `types/auth.ts`，补齐 `UserResponse` 等认证相关类型。

验收标准：

- `npx.cmd tsc --noEmit` 通过。
- `npm run build` 通过。

#### 3.3.2 前端菜单按角色显示

涉及文件：

- `frontend/src/layouts/MainLayout.tsx`
- `frontend/src/layouts/AdminLayout.tsx`
- `frontend/src/routes/index.tsx`
- `frontend/src/components/RequireAuth.tsx`
- `frontend/src/stores/useAuthStore.ts`

修改要点：

- 普通用户只显示聊天、历史会话、我的工单。
- staff 显示 FAQ、工单、看板。
- admin 显示知识库、模型配置、用户管理、系统设置。
- 路由层也要做权限拦截。

验收标准：

- 不同角色登录后菜单不同。
- 手动输入无权限路由时被拦截。

### 3.4 阶段一整体验收

- 前端构建通过。
- 聊天必须登录。
- WebSocket 鉴权可用。
- 管理接口按角色控制。
- 普通用户无法管理知识库、FAQ、模型配置。
- 普通用户无法看到完整来源。
- admin 可以管理多个模型配置并设置默认模型。

## 4. 阶段二：登录态会话持久化闭环

### 4.1 目标

打通用户、会话、消息、AI 回复、来源、意图、耗时、状态的完整链路。

### 4.2 后端任务

#### 4.2.1 扩展聊天请求结构

涉及文件：

- `backend/api/schemas.py`
- `backend/api/routes.py`

修改要点：

- `ChatRequest` 增加 `conversation_id`。
- WebSocket 消息体增加 `conversation_id`。
- 后端校验 `conversation_id` 是否属于当前用户。

验收标准：

- 用户不能使用别人的 `conversation_id` 发消息。
- 无效会话 ID 返回错误。

#### 4.2.2 后端保存用户消息和 AI 回复

涉及文件：

- `backend/api/routes.py`
- `backend/mysql_module/conversations.py`
- `backend/mysql_module/models.py`
- `backend/rag_qa/pipeline.py`

修改要点：

- 收到用户问题后保存 user message。
- AI 回复完成后保存 assistant message。
- 保存字段包括：
  - `public_sources`
  - `debug_sources`
  - `intent`
  - `latency_ms`
  - `confidence`
  - `need_handoff`
  - `status`

验收标准：

- 聊天完成后数据库中有一条 user message 和一条 assistant message。
- 刷新页面后消息仍存在。

#### 4.2.3 流式中断和异常保存

涉及文件：

- `backend/api/routes.py`
- `backend/rag_qa/pipeline.py`

修改要点：

- WebSocket 流式过程中累积 AI 内容。
- 正常完成保存 `status=completed`。
- 用户断开或停止保存 `status=interrupted`。
- LLM 异常保存 `status=error`。

验收标准：

- 用户中断后历史记录中能看到中断状态。
- 模型异常不会导致用户消息丢失。

#### 4.2.4 会话标题生成

涉及文件：

- `backend/mysql_module/conversations.py`
- `backend/api/routes.py`

修改要点：

- 新会话第一条用户消息作为标题。
- 截断 20-30 字。

验收标准：

- 新会话发送第一条消息后标题自动更新。

### 4.3 前端任务

#### 4.3.1 前端创建会话改为调用后端

涉及文件：

- `frontend/src/stores/useChatStore.ts`
- `frontend/src/services/conversationService.ts`
- `frontend/src/pages/Chat/index.tsx`
- `frontend/src/pages/Chat/ChatHistory.tsx`

修改要点：

- `newConversation()` 调用后端创建会话。
- 使用后端返回的会话 ID。
- 不再使用本地 `conv_xxx` 作为正式 ID。

验收标准：

- 新建会话后数据库有记录。
- 刷新页面后会话仍存在。

#### 4.3.2 点击历史会话加载消息

涉及文件：

- `frontend/src/stores/useChatStore.ts`
- `frontend/src/services/conversationService.ts`
- `frontend/src/pages/Chat/ChatHistory.tsx`
- `frontend/src/pages/Chat/ChatWindow.tsx`

修改要点：

- 会话列表只加载摘要。
- 点击会话时调用 `/messages` 加载消息。
- 消息加载后渲染聊天窗口。

验收标准：

- 切换会话能看到对应历史消息。
- 刷新后仍能恢复历史。

#### 4.3.3 聊天发送带 conversation_id

涉及文件：

- `frontend/src/pages/Chat/ChatInput.tsx`
- `frontend/src/hooks/useWebSocket.ts`
- `frontend/src/types/chat.ts`

修改要点：

- 发送 WebSocket 消息时带 `conversation_id`。
- 移除普通用户传 `model_config_id`。

验收标准：

- 后端能正确保存消息到对应会话。

### 4.4 阶段二整体验收

- 登录用户可以创建会话。
- 发送消息后后端落库。
- AI 回复后后端落库。
- 刷新页面后历史恢复。
- 用户不能访问别人的会话和消息。

### 5.2 后端任务

- `backend/api/schemas.py`
- `backend/main.py`

新增表建议：

```text
support_tickets
- id
- ticket_no
- user_id
- conversation_id
- message_id
- category
- priority
- status
- summary
- user_question
- ai_answer
- public_sources
- debug_sources
- assigned_to
- staff_note
- created_at
- updated_at
```

验收标准：

- 用户可以查看自己的工单。
- staff 可以查看公共池工单。
- staff 可以领取工单。

#### 5.2.2 工单公共池和领取机制

涉及文件：

- `backend/api/tickets.py`
- `backend/mysql_module/tickets.py`

接口建议：

```http
GET  /api/tickets
GET  /api/tickets/{id}
POST /api/tickets/{id}/claim
PUT  /api/tickets/{id}/status
PUT  /api/tickets/{id}/assign
PUT  /api/tickets/{id}/note
```

权限规则：

- user 只能看自己的工单。
- staff 可查看 open/processing 工单。
- staff 只能处理自己领取的工单。
- admin 可以处理和分配所有工单。

验收标准：

- 新工单 `assigned_to = null`。
- staff 领取后 `assigned_to = 当前 staff`，状态变为 `processing`。
- 非领取人 staff 不能修改该工单。

#### 5.2.3 转人工判断逻辑

涉及文件：

- `backend/rag_qa/pipeline.py`
- `backend/business/ticket_service.py`
- `backend/mysql_module/tickets.py`

触发规则：

- 用户明确要求人工。
- 连续低置信度。
- 连续没帮助。
- 高风险关键词。
- 订单物流多次缺信息。
- LLM 或业务接口异常。

验收标准：

- 用户说“转人工”会生成工单。
- 低置信度连续出现会生成工单或提示转人工。
- 生成工单后聊天回复包含工单号。

#### 5.2.4 订单/物流服务层

涉及文件：

- `backend/business/order_service.py`
- `backend/business/logistics_service.py`
- `backend/rag_qa/pipeline.py`
- `backend/rag_qa/ecommerce_mock.py`

修改要点：

- 新增服务层接口，保留 `user_id` 参数。
- 当前实现仍使用 mock。
- mock 数据按用户隔离。
- pipeline 不直接调用 `query_order()`、`query_logistics()`。

验收标准：

- 不同用户查询到不同 mock 订单。
- 用户不能查到别人的订单。
- 后续替换真实接口时只需替换 service 实现。

#### 5.2.5 Slot Filling 和追问

涉及文件：

- `backend/business/order_service.py`
- `backend/business/logistics_service.py`
- `backend/rag_qa/intent_recognizer.py`
- `backend/rag_qa/pipeline.py`

修改要点：

- 提取订单号、运单号、手机号后四位、商品名、时间范围。
- 信息不足时追问。
- 有最近订单时返回可选订单列表。

验收标准：

- “我的快递到哪了”不会随机返回订单。
- 缺订单号时会追问或展示最近订单。
